# Maven Stack Upgrade Tool — 배경(Trigger)

- 작성일: 2026-08-10
- 목적: 보고서의 "왜 지금 이 도구가 필요한가" 절에 쓸 배경 자료. 실제 사고 사례 → 공통 패턴 → 제도 변화 → 이 도구가 겨냥하는 지점 순으로 정리한다.

## 1. 한 줄 요약

지난 10여 년간 보도된 대형 침해사고 상당수는 **제로데이가 아니라, 패치가 이미 공개돼 있던 오픈소스 취약점을 제때 적용하지 않아** 발생했다. 즉 기술적으로 막을 수 없던 공격이 아니라 **의존성 파악과 업그레이드 실행의 실패**였고, 이 도구가 자동화하려는 지점이 정확히 그 부분이다.

### 2.1 상세 — Equifax (가장 자주 인용되는 사례)

- 2017년 3월 7일 Apache가 Struts 2의 원격코드실행 취약점 패치를 공개했고, 다음 날 US-CERT가 경보를 냈다. Equifax 내부에도 패치 공지가 돌았다.
- 그럼에도 **취약한 Struts가 어느 서버에 들어 있는지 조직이 파악하지 못했다.** 내부 스캔은 해당 서버를 찾아내지 못했고, 그 상태로 5월경 침투가 시작돼 7월 29일에야 탐지됐다.
- 미 하원 감독위원회 보고서는 근본 원인으로 자산·의존성 인벤토리 부재와 패치 검증 프로세스 실패를 지목했다.
- **시사점**: 실패 지점은 "패치를 안 만들어서"가 아니라 **"어디에 무엇이 쓰이는지 몰라서"**였다.

### 2.2 상세 — Log4Shell (전이 의존성 문제의 교과서)

- 2021년 12월 CVE-2021-44228 공개 직후 전 세계적으로 대량 스캐닝이 시작됐다.
- 문제는 대부분의 조직이 Log4j를 **직접 선언하지 않았다**는 점이다. Spring Boot 등 상위 프레임워크를 통해 **전이 의존성(transitive dependency)** 으로 딸려 들어와 있었기 때문에, `pom.xml`만 봐서는 영향 여부를 판단할 수 없었다.
- 그 결과 "우리가 영향받는가"를 확인하는 데만 수 주가 걸린 조직이 많았고, 그 사이에 위 사례들처럼 실제 침해로 이어졌다.
- **시사점**: 의존성 트리 전체를 기계적으로 해석하지 않으면 영향 범위 산정 자체가 불가능하다.

## 3. 공통 패턴

1. **거의 모두 기지(known) 취약점이었다.** 패치는 이미 있었다. 실패한 것은 패치 관리이지 방어 기술이 아니다.
2. **자산·의존성 인벤토리 부재가 결정타였다.** Equifax도 Log4Shell도 "어디에 쓰이는지 모른다"가 병목이었다.
3. **직접 의존성보다 전이 의존성이 위험하다.** 개발자가 선언하지 않은 라이브러리가 실제 취약점의 대부분을 차지한다.
4. **공개에서 대량 공격까지 수 시간~수일.** 분기 단위 정기 릴리스 주기로는 따라갈 수 없다.
5. **미조치 상태가 길수록 비용이 지수적으로 커진다.** 업그레이드 지연은 기술부채가 아니라 **누적되는 노출 시간**이다.

> 참고: XZ Utils 백도어(2024)나 npm 워름 사고처럼 **악성 코드가 주입되는 공급망 침투**는 성격이 다른 축이다. 이 문서가 다루는 것은 "이미 공개된 취약점을 고치지 않은" 축이며, 보고서에서도 두 축은 구분해 서술하는 편이 좋다.

## 4. 제도·규제 흐름

- **미국 행정명령 14028(2021)**: 연방정부 납품 소프트웨어에 SBOM(Software Bill of Materials) 제출을 요구. Log4Shell 사태가 이 흐름을 가속시켰다.
- **EU 사이버복원력법(CRA)**: 2024년 발효. 취약점 신고 의무는 2026년 9월부터, 주요 의무는 2027년 12월부터 적용 예정. 디지털 제품에 대해 지원기간 내 보안 업데이트 제공과 SBOM 관리를 의무화한다.
- **국내**: 과기정통부·KISA의 소프트웨어 공급망 보안 가이드라인을 통해 SBOM 기반 관리가 권고되고 있으며, 공공 조달을 중심으로 요구 수준이 높아지는 추세다.
- **지원 종료(EOL) 리스크**: Spring Boot 2.x 계열은 OSS 지원이 종료되어 신규 CVE에 대한 커뮤니티 패치가 제공되지 않는다. 구버전 스택에 머무르는 것은 "아직 취약점이 없는" 상태가 아니라 **"패치를 받을 수 없는"** 상태다.

## 5. 이 도구가 겨냥하는 지점

위 패턴에 대응해 Maven Stack Upgrade Tool이 해결하려는 것은 다음과 같다.

| 사고에서 드러난 실패 | 이 도구의 대응 |
|---|---|
| 어디에 무엇이 쓰이는지 모름 | 임의의 Maven 프로젝트를 인입해 의존성 트리와 취약점을 기계적으로 스캔(OWASP Dependency-Check / Trivy) |
| 전이 의존성 미가시성 | 스캔 결과를 직접/전이 구분 없이 병합해 실제 영향 범위로 제시 |
| 지원 종료 스택에 잔류 | 1단계에서 **Java 21 / Spring Boot 4.1 / Spring Cloud 2025.1 / Spring AI 2.0** 으로 일괄 마이그레이션 — 스택 상향만으로 다수의 CVE가 한 번에 해소됨 |
| 스택을 올려도 남는 개별 취약점 | 2단계에서 잔여 개별 CVE를 스캔·패치 |
| 업그레이드 실행 부담(수작업·회귀 위험) | OpenRewrite 기반 자동 변환 + 단계별 체크포인트/롤백 + 자가검증 루프 |
| 변경 내역 검증 곤란 | diff / 리포트 / AI 인수인계 가이드 산출, **자동 커밋·푸시는 하지 않음**(담당자 검토 후 반영) |

즉 이 도구는 "취약점을 알려주는 도구"가 아니라, **알고도 못 고치던 이유(실행 비용)를 제거하는 도구**로 포지셔닝된다.
